### Architecture Decision: New Standalone Process
**Rationale for New Process:**
- Tutorial system is distinct from game mechanics (educational vs gameplay)
- Tutorial system requires progression tracking and skill validation
- Separation allows focused testing of tutorial flow behavior
- Process size management: tutorial logic estimated ~25-35KB with embedded text
- Future extensibility: tutorial system may expand with new tutorial types

**Implementation Strategy:**
- Create new `processes/tutorial-engine.lua` process
- Define tutorial type constants and text content embedded in process
- Implement handlers: StartTutorial, CompleteTutorialStep, GetTutorialProgress, ValidateTutorialSkill
- Maintain stateless design with all tutorial state passed via GameState JSON
- Use deterministic progression logic for reproducible tutorial behavior

**Process Architecture Pattern** [Source: docs/architecture/tech-stack.md#process-communication-protocol]
```lua
-- New tutorial-engine.lua process
-- Stateless design with embedded tutorial definitions

local json = require("json")

-- Tutorial Type Constants
local TutorialType = {
  INTRO = "INTRO",
  ACCESS_MENU = "ACCESS_MENU",
  MENU = "MENU",
  STARTER_SELECT = "STARTER_SELECT",
  POKEDEX = "POKEDEX",
  POKERUS = "POKERUS",
  STAT_CHANGE = "STAT_CHANGE",
  SELECT_ITEM = "SELECT_ITEM",
  EGG_GACHA = "EGG_GACHA"
}

-- Tutorial Definitions (embedded)
local TUTORIAL_DEFINITIONS = {
  [TutorialType.INTRO] = {
    text = "Welcome to PokéRogue!...",
    prerequisites = {},
    skillChecks = {},
    overlay = {required = false},
    nextStep = "ACCESS_MENU"
  },
  -- ... (other tutorial definitions)
}

-- Helper functions for tutorial progression
local function startTutorial(tutorialType, playerState)
  -- Check if already completed
  if playerState.completedTutorials[tutorialType] then
    return {success = true, shouldDisplay = false}
  end

  -- Return tutorial definition
  local tutorial = TUTORIAL_DEFINITIONS[tutorialType]
  return {
    success = true,
    shouldDisplay = true,
    tutorialType = tutorialType,
    text = tutorial.text,
    overlay = tutorial.overlay
  }
end

-- Handler registration (individual handlers for each action)
Handlers.add("start-tutorial",
  Handlers.utils.hasMatchingTag("Action", "StartTutorial"),
  function(msg)
    local tutorialType = msg.TutorialType
    if not tutorialType then
      ao.send({
        Target = msg.From,
        Action = "Error",
        Error = "TutorialType required"
      })
      return
    end

    local playerState = json.decode(msg.Data or "{}")
    local result = startTutorial(tutorialType, playerState)

    ao.send({
      Target = msg.From,
      Action = "SaveState",
      Success = "true",
      Data = json.encode(result)
    })
  end
)

-- Additional handlers for tutorial progression
```

### Technical Constraints

**AO Runtime Constraints** [Source: docs/architecture/tech-stack.md#performance-constraints]
- Execution Timeout: 5-second limit per message handler
- File Size Limit: 500KB maximum per process file
- Estimated Process Size: ~25-35KB for tutorial logic and text
- Memory Constraints: Limited by AO network specifications
- Deterministic Execution: Predictable progression logic (no randomness)

**AO Compliance Requirements** [Source: docs/architecture/tech-stack.md#process-implementation-requirements]
- Monolithic Design: All tutorial logic in single file
- Handler Pattern: Use `Handlers.add()` with individual handlers per action (no multi-action handlers)
- Error Handling: Direct validation and error responses, avoid unnecessary pcall usage
- **CRITICAL**: Never use pcall for simple data access (table lookups, parameter validation)
- **CRITICAL**: Use pcall ONLY for operations that genuinely might fail (JSON parsing from untrusted sources)
- Available Globals: ao.send(), ao.id, Handlers, json, standard Lua (string, table, math)

**Forbidden Operations** [Source: CLAUDE.md#ao-process-implementation-guidelines]
- `require()` - No external module loading (except require("json") which is permitted)
- `os.time()` - Use `msg.Timestamp` instead
- `io` - No file system access
- `debug` - Debug library unavailable
- Network operations - Only through ao.send()

**Coding Standards** [Source: docs/architecture/coding-standards.md]
- Functions: camelCase (e.g., `startTutorial()`, `validateSkill()`)
- Variables: camelCase (e.g., `tutorialState`, `progressResult`)
- Constants: UPPER_SNAKE_CASE (e.g., `TUTORIAL_DEFINITIONS`, `DEFAULT_TEXT`)
- Tables/Objects: PascalCase (e.g., `TutorialType`, `ProgressState`)
- Files: kebab-case (e.g., `tutorial-engine.lua`)
- All message responses must include Success tag: `Success = "true"` or `Success = "false"`

**Deterministic Behavior Requirements**
- All tutorial progression must be predictable and reproducible
- Skill validation must be consistent across executions
- Tutorial flag tracking must be accurate and verifiable
- No randomness in tutorial flow or branching logic

- **Benefits**: Centralized tutorial flow coordination, consistent progression logic, easy extensibility

**Tutorial System Flow**
This story focuses on tutorial progression and tracking:
1. **Client Request**: Player encounters tutorial trigger point
2. **Tutorial Check**: Engine validates if tutorial already completed
3. **Tutorial Start**: Return tutorial definition with text and requirements
4. **Progress Tracking**: Monitor player progression through tutorial steps
5. **Skill Validation**: Verify player demonstrates required skills
6. **Step Completion**: Mark tutorial step complete, advance to next
7. **Tutorial Completion**: Save tutorial flag, update statistics
8. **Response**: Return updated tutorial state and next actions

**Key Integration Points**:
- Game data: Tutorial flag persistence in save state
- UI system: Tutorial text display and overlay management
- Input system: Skill check validation based on player actions
- Progression system: Tutorial completion affects game flow
- Coordinator ensures atomic operations (flag save, state update)

**Migration Strategy**
- Extract tutorial definitions from `src/tutorial.ts` handler functions
- Port tutorial flow orchestration from `handleTutorial()` function
- Port tutorial flag persistence from `src/system/game-data.ts`
- Port overlay management metadata from `showTutorialOverlay()` / `hideTutorialOverlay()`
- Stateless design: no process-local state, all data derived from GameState
- Single-process coordination: all tutorial logic in one process
