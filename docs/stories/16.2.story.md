# Story 16.2: Trainer Encounter Migration

**Epic:** Epic 16 - World Progression & Biome System
**Status:** Done
**Created:** January 10, 2025
**Updated:** January 10, 2025 (Marked Complete - Foundation Milestone)
**Assigned:** Trainer System Engineering Team

## Story Statement
As a **trainer encounter engineer**,
I want **trainer encounter and battle systems migrated to stateless AO process**,
so that **trainer generation and battle mechanics maintain identical behavior to TypeScript**.

## Acceptance Criteria
1. Trainer generation algorithms produce statistically identical team composition and level distributions
2. Trainer AI behavior maintains identical battle decision-making and strategy patterns
3. Trainer encounter probability maintains identical spawn rate calculation and area distribution
4. Trainer reward calculation maintains identical experience and prize distribution behavior
5. Trainer progression tracking maintains identical defeat recording and achievement recognition
6. Trainer dialogue and interaction maintains identical text presentation and choice handling
7. Complex trainer scenarios maintain identical battle flow and interaction resolution
8. Comprehensive testing validates 100% trainer encounter system behavioral and probability parity

## Dev Notes

### Previous Story Insights
- Story 16.1 completed Biome Progression Migration with 23.22KB process achieving 100% test coverage (27/27 passing)
- Epic 16 established: biome graph-based progression, weighted selection, Map modifier player choice, END biome handling
- Key lessons from Story 16.1:
  - Monolithic design with all dependencies embedded (no require() except json)
  - Error handling: Direct validation with ao.send() error responses, avoid unnecessary pcall
  - Proper AO message coordination using ao.send() with structured Target, Action, Data
  - Process size targets: 10-15KB for simple processes, 35-45KB for complex logic, 70-80KB for large embedded data
  - ADP v1.0 compliance required with Info handler for self-documentation
  - Tag-based message parameters for simple values, Data field for complex structures
  - Avoid module-level returns - use message passing exclusively
  - All tag values MUST be strings: tostring(number), "true"/"false" for booleans
  - Timestamp handling: CRITICAL - Use msg.Timestamp, NEVER os.time()
- **COMPLEXITY ASSESSMENT**: Trainer system is highly complex with extensive data requirements:
  - 300+ trainer types with full configuration (TrainerType enum)
  - Party generation algorithms with 6 different selection methods
  - AI decision-making with matchup score calculations
  - Biome-specific trainer pools with rarity tiers (COMMON through ULTRA_RARE)
  - Signature species for Gym Leaders, Elite Four, Champions (stored per-trainer)
  - Dynamic party templates with strength-based level scaling
  - Money reward calculation with trainer-specific multipliers
  - Expected process size: 350-550KB (70-110% of 500KB limit) - requires data optimization
- **REFERENCE SOURCE**: TypeScript implementation across multiple files:
  - `typescript-reference/src/field/trainer.ts` - Trainer class, party generation, levels (500+ lines)
  - `typescript-reference/src/data/trainers/trainer-config.ts` - TrainerConfig, AI, rewards (3000+ lines)
  - `typescript-reference/src/data/trainers/trainer-party-template.ts` - Party templates (300+ lines)
  - `typescript-reference/src/data/balance/signature-species.ts` - Gym Leader/Elite Four Pokemon (200+ lines)
  - `typescript-reference/src/enums/trainer-type.ts` - 300+ trainer type definitions
  - `typescript-reference/src/enums/trainer-pool-tier.ts` - Rarity tier definitions
- **PARITY APPROACH**: All trainer generation, level calculation, species selection, and AI logic must match TypeScript exactly
- **DATA EMBEDDING STRATEGY**: Large trainer configuration data requires optimization:
  - Trainer configs: 200-300KB (REQUIRED - core configuration)
  - Signature species: 10-15KB (REQUIRED - named trainer Pokemon)
  - Party templates: 5KB (REQUIRED - composition templates)
  - Biome trainer pools: 100-200KB (REQUIRED - encounter rates)
  - Species/Move databases: NOT embedded (reference external processes)
  - Dialogue strings: NOT embedded (reference localization process)
  - Expected process size: 350-550KB (may require data compression or sharding)
- Testing validation patterns: Unit tests with aolite, integration tests with aos-local, parity tests against TypeScript

-- Incoming: Generate trainer encounter
msg = {
    Action = "GenerateTrainer",
    WaveIndex = "40",
    BiomeType = "1",          -- BiomeId.PLAINS

    Action = "TrainerGenerated",

    currentDefScore = 1 / 0.5 = 2.0         -- Resists Rock
    currentAtkScore = 2.0 * 1.5 = 3.0       -- Super effective STAB
    currentMatchup = 2.0 * 3.0 * 1.25 = 7.5 -- Outspeeds

    -- Best switch: Vaporeon vs Graveler
    vaporeonDefScore = 1 / 1.0 = 1.0        -- Neutral defense
    vaporeonAtkScore = 2.0 * 1.5 = 3.0      -- Super effective STAB Water
    vaporeonMatchup = 1.0 * 3.0 * 1.25 = 3.75  -- Outspeeds

    -- Switch threshold
    switchThreshold = 7.5 * 3 = 22.5        -- Regular trainer (3x)
    switchMultiplier = 1.0                  -- First switch

    -- Switch decision: 3.75 * 1.0 = 3.75 < 22.5 (DO NOT SWITCH)
}

trainer-encounter-engine -> battle-engine {

    ShouldSwitch = "false",

### Technical Constraints
[Source: architecture/tech-stack.md]
- **Execution Timeout**: 5-second limit per message handler
- **File Size Limit**: 500KB maximum per process file (target 350-550KB with optimization)
- **Monolithic Design**: All trainer metadata embedded, no external imports except json
- **Handler Pattern**: Use Handlers.add() with tag matching, not direct assignment
- **Message Protocol**: JSON-encoded data with structured ao.send() responses
- **Timestamp Handling**: CRITICAL - Use msg.Timestamp, NEVER os.time()
- **Error Handling**: Direct validation with ao.send() error responses, avoid unnecessary pcall
- **Tag Values**: All tag values MUST be strings: tostring(number), "true"/"false" for booleans
- **Trainer Config Data**: Requires embedded 200-300KB configuration data (all trainer types)
- **Signature Species**: Requires embedded 10-15KB signature species data (gym leaders, elite four)
- **Biome Pools**: Requires embedded 100-200KB biome-specific trainer pools
- **Deterministic RNG**: Use math.random() with manual seeding for reproducible generation
- **Species/Move Lookups**: Reference external processes, do not embed full databases

### Security Requirements
- **Input Validation**: All wave indexes, trainer types, and biome types must be validated
- **Authorization**: Player can only generate trainers for their current game context
- **State Integrity**: Ensure trainer generation is deterministic and reproducible
- **Seed Management**: RNG seeds must be controlled to prevent exploitation
- **Level Caps**: Enforce maximum level constraints to prevent overflow
- **Party Size Limits**: Validate party size does not exceed 6 Pokemon
- **Species Validation**: Ensure generated species are valid and eligible for trainer
