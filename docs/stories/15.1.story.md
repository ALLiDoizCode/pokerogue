# Story 15.1: Passive Ability System Migration

**Epic:** Epic 15 - Passive Abilities & Unlockables
**Status:** Done
**Created:** September 30, 2025
**Assigned:** Passive Ability Engineering Team

## Story Statement
As a **passive ability engineer**,
I want **passive ability mechanics and effects migrated to stateless AO process**,
so that **passive ability activation and effects maintain identical behavior to TypeScript**.

## Acceptance Criteria
1. Passive ability trigger conditions evaluate identically to TypeScript implementation
2. Passive ability effect calculations produce mathematically identical modifier applications
3. Passive ability stacking rules maintain identical interaction resolution and limit enforcement
4. Passive ability persistence maintains identical state tracking across all game scenarios
5. Passive ability interaction with active abilities maintains identical priority and resolution behavior
6. Passive ability upgrade mechanics maintain identical progression logic and enhancement calculation
7. Complex passive ability scenarios maintain identical effect calculation and interaction resolution
8. Comprehensive testing validates 100% passive ability system behavioral and mathematical parity

## Dev Notes

### Previous Story Insights
- Story 14.4 completed Egg Hatching and Incubation Migration with `egg-hatching-engine.lua` handling step progression, Pokemon generation, and mass hatching operations
- Critical lessons from Epic 14 stories:
  - Monolithic design with all dependencies embedded (no require() statements except json)
  - Direct error handling without excessive pcall usage (only for genuinely unpredictable operations)
  - Proper AO message coordination between processes using ao.send() with structured Target, Action, Data
  - Process size targets: 35-45KB for complex logic processes (well within 500KB limit)
  - ADP v1.0 compliance required with Info handler for self-documentation
  - Tag-based message parameters for simple values, Data field for complex structures
  - Avoid module-level returns - use message passing exclusively
  - All tag values MUST be strings: tostring(number), "true"/"false" for booleans

  - Passive abilities are **alternate abilities** that Pokemon can unlock and enable alongside their normal ability
  - Not a separate system but part of the core ability mechanics
  - Integration required with existing `ability-engine.lua` and battle mechanics
  - 900+ Pokemon species have unique passive ability configurations (starterPassiveAbilities table)

### Coordinator Integration Sequences
#### Passive Ability Activation in Battle Workflow
```lua
-- Step 1: Battle system detects passive trigger event
BattleEngine -> coordinator-process {
    Action = "PassiveTriggerEvent",
    PokemonId = "pokemon_123",
    Event = "defeated_opponent",
    BattleContext = {...}
}

-- Step 2: Coordinator checks passive state
coordinator-process -> passive-ability-engine {
    Action = "CanApplyPassive",
    PokemonId = "pokemon_123",
    BattleContext = {...}
}

-- Step 3: Passive engine validates state
passive-ability-engine -> coordinator-process {
    Action = "PassiveApplicationResult",
    CanApply = "true",
    AbilityId = "beast_boost"
}

-- Step 4: Coordinator requests ability effect
coordinator-process -> ability-engine {
    Action = "GetAbilityEffect",
    AbilityId = "beast_boost",
    TriggerContext = {...}
}

-- Step 5: Ability engine calculates effect
ability-engine -> coordinator-process {
    Action = "AbilityEffectResult",
    Data = json.encode({
        statBoosts = { attack = 1 }
    })
}

-- Step 6: Coordinator applies effect to battle
coordinator-process -> battle-engine {
    Action = "ApplyPassiveEffect",
    PokemonId = "pokemon_123",
    EffectData = {...}
}

-- Step 7: Battle engine confirms application
battle-engine -> coordinator-process {
    Action = "PassiveEffectApplied",
    Success = "true"
}

-- Step 8: Return to original caller
coordinator-process -> Original Caller {
    Action = "PassiveTriggerComplete",
    Data = json.encode({
        success = true,
        effectDescription = "Attack rose!"
    })
}
```

#### Passive Unlock/Upgrade Workflow
```lua
-- Step 1: Client requests passive unlock
ClientRequest -> coordinator-process {
    Action = "UnlockPassive",
    PlayerId = "player_456",
    SpeciesId = "bulbasaur",
    Cost = "50"
}

-- Step 2: Coordinator validates player resources
coordinator-process -> player-progression-engine {
    Action = "CheckResource",
    PlayerId = "player_456",
    ResourceType = "starter_candy",
    Amount = "50"
}

-- Step 3: Resource validation
player-progression-engine -> coordinator-process {
    Action = "ResourceCheckResult",
    Available = "true",
    CurrentAmount = "120"
}

-- Step 4: Coordinator executes unlock
coordinator-process -> passive-ability-engine {
    Action = "UnlockPassive",
    PlayerId = "player_456",
    SpeciesId = "bulbasaur"
}

-- Step 5: Passive engine updates state
passive-ability-engine -> coordinator-process {
    Action = "PassiveUnlocked",
    Success = "true",
    SpeciesId = "bulbasaur"
}

-- Step 6: Coordinator deducts cost
coordinator-process -> player-progression-engine {
    Action = "DeductResource",
    PlayerId = "player_456",
    ResourceType = "starter_candy",
    Amount = "50"
}

-- Step 7: Resource deduction confirmed
player-progression-engine -> coordinator-process {
    Action = "ResourceDeducted",
    NewAmount = "70"
}

-- Step 8: Return to client
coordinator-process -> Client {
    Action = "UnlockComplete",
    Data = json.encode({
        success = true,
        speciesId = "bulbasaur",
        remainingCandy = 70
    })
}
```

### Technical Constraints
[Source: architecture/tech-stack.md]
- **Execution Timeout**: 5-second limit per message handler
- **File Size Limit**: 500KB maximum per process file (target 35-45KB based on previous stories)
- **Monolithic Design**: All dependencies embedded, no external imports except json
- **Handler Pattern**: Use Handlers.add() with tag matching
- **Message Protocol**: JSON-encoded data with structured ao.send() responses
- **Timestamp Handling**: Use msg.Timestamp, never os.time()
- **Error Handling**: Direct validation with ao.send() error responses, avoid unnecessary pcall
- **Large Data Structure**: starterPassiveAbilities table is 1100+ lines - must be embedded efficiently

### Security Requirements
- **Input Validation**: All species IDs and Pokemon IDs must be validated before processing
- **Authorization**: Player can only unlock/upgrade passives for their own account
- **Resource Validation**: Verify sufficient starter candy before processing unlocks/upgrades
- **State Integrity**: Ensure passive unlock state cannot be corrupted or exploited
- **Battle Context Validation**: Passive triggers must validate battle state to prevent abuse
- **Tier Limits**: Enforce maximum upgrade tier constraints per species
