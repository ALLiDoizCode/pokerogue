## Story Statement
As a **battle state engineer**,  
I want **comprehensive battle state tracking migrated to stateless AO process**,  
so that **battle state consistency and persistence match TypeScript implementation exactly**.

## Acceptance Criteria
1. Pokemon active state tracking maintains identical health, status, and temporary modifications
2. Field condition tracking (weather, terrain, tricks) persists identically across turns
3. Battle participant state (party, benched Pokemon) maintains complete consistency
4. Move history and usage tracking maintains identical data structure and accessibility
5. Battle event logging produces identical records for replay and analysis functionality
6. State serialization/deserialization maintains complete data integrity during battle saves
7. Memory management ensures no state corruption during complex battle sequences
8. Comprehensive testing validates state consistency across extended battle scenarios

- All state transitions must be atomic and reversible for consistency
- Battle state must be completely deterministic for replay functionality
- All AO message responses must include success boolean
- State validation must occur at every transition point
- Never hardcode Pokemon/Move/Item data - always reference database tables

**Performance Constraints** [Source: architecture/tech-stack.md#Performance Constraints]:
- Execution Timeout: 5-second limit per message handler
- File Size Limit: 500KB maximum per process file
- Memory Constraints: Limited by AO network specifications
- Message Size: Practical limits on JSON payload size for state serialization

**AO Runtime Specifications** [Source: architecture/tech-stack.md#AO Runtime Specifications]:
- Monolithic Design: All dependencies embedded in single file
- Handler Pattern: Use `Handlers.add()` with tag matching
- Available globals: `ao.send()`, `ao.id`, `Handlers`, `json`
- No `require()` statements allowed

3. **Atomic Operations**: State updates must be atomic to prevent partial updates and corruption
4. **Access Control**: State modification requests should be validated against battle participation
5. **Memory Safety**: Handle large state objects without memory leaks or overflow
6. **Replay Security**: Maintain complete determinism for battle replay functionality
7. **Anti-Corruption**: Validate all state data against game rules to prevent invalid states
