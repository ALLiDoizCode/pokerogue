### Architecture Decision: New Standalone Process
**Rationale for New Process:**
- Community events have distinct lifecycle from seasonal events (user-generated vs system-defined)
- Community coordination requires different data structures (collective progress, participant tracking)
- Separation of concerns: seasonal events (time-based content) vs community events (participation-based coordination)
- Process size management: community event logic estimated ~50-70KB, keeping processes focused
- Future extensibility: community features may expand beyond timed event scope

**Implementation Strategy:**
- Create new `processes/community-event-engine.lua` process
- Define community event data model embedded in process
- Implement handlers: CreateEvent, TrackContribution, GetProgress, DistributeRewards, SyncEvent
- Maintain stateless design with all state passed via GameState JSON
- Use msg.Timestamp for all timing and synchronization logic

**Handler: CreateCommunityEvent** [Source: Architecture requirements for AO message patterns]
- **Trigger Tag**: `Action = "CreateCommunityEvent"`
- **Required Parameters**: `msg.EventConfig` (JSON with event configuration)
- **Response**: Created community event with initial state
- **Error Conditions**: Invalid event configuration, invalid timestamp ranges
- **Example**:
  ```lua

  -- Response
  {
    Action = "SaveState",

      eventId = "winter-challenge-2025",
      status = "PENDING",
      name = "Winter Community Challenge",
      startDate = 1734739200,
      endDate = 1735948800
    }),
    Success = "true"
  }
  ```

  LOW = "LOW" -- 51-100%

-- Helper functions for event management
local function getEventById(eventId) ... end
local function validateEventConfig(config) ... end
local function calculateProgress(goalId, contributions) ... end
local function detectMilestones(progress, milestones) ... end
local function calculateRewardTiers(participants, contributions) ... end

-- Handler registration (individual handlers for each action)
Handlers.add("create-community-event",
  Handlers.utils.hasMatchingTag("Action", "CreateCommunityEvent"),
  function(msg)
    local eventConfig = json.decode(msg.EventConfig or "{}")

    if not eventConfig.name or not eventConfig.startDate or not eventConfig.endDate then
      ao.send({
        Target = msg.From,
        Action = "Error",
        Error = "Event name, startDate, and endDate required"
      })
      return
    end

    local event = createEvent(eventConfig)

    ao.send({
      Target = msg.From,
      Action = "SaveState",
      Data = json.encode({
        eventId = event.eventId,
        status = event.status,
        name = event.name
      }),
      Success = "true"
    })
  end
)

### Technical Constraints

**AO Runtime Constraints** [Source: docs/architecture/tech-stack.md#performance-constraints]
- Execution Timeout: 5-second limit per message handler
- File Size Limit: 500KB maximum per process file
- Estimated Process Size: ~50-70KB for community event logic
- Memory Constraints: Limited by AO network specifications
- Deterministic Execution: Use msg.Timestamp for timing, no os.time()

**AO Compliance Requirements** [Source: docs/architecture/tech-stack.md#process-implementation-requirements]
- Monolithic Design: All community event logic in single file
- Handler Pattern: Use `Handlers.add()` with individual handlers per action (no multi-action handlers)
- Error Handling: Direct validation and error responses, avoid unnecessary pcall usage
- **CRITICAL**: Never use pcall for simple data access (table lookups, parameter validation)
- **CRITICAL**: Use pcall ONLY for operations that genuinely might fail (external JSON parsing from untrusted sources)
- Available Globals: ao.send(), ao.id, Handlers, json, standard Lua (string, table, math)

**Forbidden Operations** [Source: CLAUDE.md#ao-process-implementation-guidelines]
- `require()` - No external module loading (except require("json") which is permitted)
- `os.time()` - Use `msg.Timestamp` instead
- `io` - No file system access
- `debug` - Debug library unavailable
- Network operations - Only through ao.send()
- Math.random() - Use deterministic seeded RNG for any randomness

**Coding Standards** [Source: docs/architecture/coding-standards.md]
- Functions: camelCase (e.g., `trackContribution()`, `calculateProgress()`)
- Variables: camelCase (e.g., `communityEvent`, `goalProgress`)
- Constants: UPPER_SNAKE_CASE (e.g., `EVENT_STATUS`, `REWARD_TIER`)
- Tables/Objects: PascalCase (e.g., `CommunityEvent`, `GoalProgress`)
- Files: kebab-case (e.g., `community-event-engine.lua`)
- All message responses must include Success tag: `Success = "true"` or `Success = "false"`

**Timestamp Handling Requirements**
- All event timing must use msg.Timestamp (UTC Unix timestamp in milliseconds)
- Event activation: `timestamp >= startDate and timestamp < endDate`
- Never use os.time() - always use msg.Timestamp
- Document timestamp units (milliseconds) in all handlers
- Validate timestamp ranges (positive integers, reasonable date ranges)

**Contribution Tracking Requirements**
- Validate all contributions for eligibility before recording
- Prevent duplicate contributions from same player for same action
- Implement rate limiting to prevent abuse (max contributions per time window)
- Track unique participant count for goal types requiring unique participation
- Aggregate contributions deterministically (sum, count, etc.)
- Persist contribution history in GameState JSON

**Reward Distribution Fairness**
- Tier-based allocation: HIGH (top 10%), MEDIUM (11-50%), LOW (51-100%)
- Proportional rewards based on contribution percentage
- Minimum participation threshold for reward eligibility
- Ensure all participants receive at least participation rewards
- Track reward claiming to prevent double-claiming
- Document reward calculation algorithms clearly

**Rationale Analysis**:
1. ✅ **Separation of Concerns**: Community events (user-generated, participation-based) vs seasonal events (system-defined, time-based content)
