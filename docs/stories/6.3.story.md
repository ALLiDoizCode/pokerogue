# Story 6.3: Terrain Effect Migration

**Epic:** Epic 6 - Status Effects & Environmental Systems  
**Status:** Done
**Created:** September 25, 2025  
**Assigned:** Terrain Effect Engineering Team  

## Story Statement
As a **terrain effect engineer**,  
I want **battlefield terrain effects migrated to stateless AO process**,  
so that **terrain mechanics and interactions maintain identical behavior to TypeScript**.

## Acceptance Criteria
1. All terrain types (electric, grassy, misty, psychic) apply identical effects
2. Terrain duration and overwrite mechanics maintain identical behavior
3. Terrain interaction with move types and power maintains mathematical precision
4. Terrain effect on status conditions maintains identical prevention and interaction rules
5. Terrain interaction with abilities and items maintains identical priority behavior
6. Terrain visualization and battle messaging maintains identical presentation
7. Terrain removal and neutralization mechanics behave identically to TypeScript
8. Comprehensive testing validates 100% terrain effect behavioral parity

### API Specifications
**Message Protocol** [Source: architecture/tech-stack.md#46-68]:
```lua
-- Incoming Message Structure for Terrain Operations
msg = {
    Action = "ProcessLogic",
    Data = {
        operation = "setTerrain", -- or "processTerrainTurn", "clearTerrain", "getTerrainInfo", "checkMoveBlocking"
        gameState = {
            battle = {
                conditions = { 
                    terrain = { terrainType = "ELECTRIC", turnsLeft = 5 },
                    weather = { weatherType = "RAIN", turnsLeft = 3 } -- Can coexist
                },
                playerParty = { /* Pokemon data for type multipliers */ },
                enemyParty = { /* Pokemon data for grounding checks */ }
            },
            battleSeed = "deterministic_seed"
        },
        parameters = {
            terrainType = "ELECTRIC", -- Using TypeScript names: MISTY, ELECTRIC, GRASSY, PSYCHIC
            duration = 5, -- turns (0 for permanent)
            overwrite = true, -- whether to replace existing terrain
            targetPokemon = { /* Pokemon for status/move interaction checks */ },
            moveData = { /* Move data for blocking/power checks */ }
        }
    },
    Timestamp = msg.Timestamp or 0
}

-- Response Structure with Terrain Data
ao.send({
    Target = msg.From,
    Action = "SaveState",
    Data = json.encode({
        success = true,
        terrain = {
            terrainType = "ELECTRIC",
            turnsLeft = 4, -- decremented if processed turn
            isActive = true
        },
        effects = {
            typeMultiplier = 1.3, -- for Electric moves on Electric terrain
            statusPrevented = false, -- for status condition interactions
            moveBlocked = false, -- for priority move blocking
            pokemonAffected = { /* List of affected Pokemon */ }
        },
        messages = {
            "The battlefield became electrified!"
        }
    }),
    Error = error_message, -- Optional
    ProcessId = ao.id,
    Timestamp = tostring(msg.Timestamp or 0)
})
```

**Handler Registration Pattern** [Source: CLAUDE.md - AO Process Implementation Guidelines]:
- MUST use individual handlers for each terrain action (no multi-action handlers)
- Use Handlers.add() with tag matching: SetTerrain, ProcessTerrainTurn, ClearTerrain, GetTerrainInfo, CheckMoveBlocking
- Wrap operations in pcall only when they might fail (JSON parsing, not simple terrain lookups)

- Match TypeScript Math.floor/Math.ceil exactly for multiplier calculations
- Include success boolean in all responses
- Reference embedded database tables for move/Pokemon type data
- Maintain deterministic behavior for replay capability
