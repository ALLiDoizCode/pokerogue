### API Specifications

**Message Protocol for Item Interaction Operations** [Source: architecture/tech-stack.md#process-communication-protocol]:
```lua
-- Incoming Message Structure for Item Interaction Operations
msg = {
    Action = "ProcessLogic",
    Data = {
        operation = "calculateInteraction", -- or "stackModifiers", "applyDuration", "resolveConflict", "validateCombination"
        gameState = {
            player = { 
                inventory = {
                    items = {}, -- Current item inventory for interaction calculations
                    modifiers = {} -- Current modifiers for stacking and precedence evaluation
                },
                progression = {
                    wave = 1, -- Current wave for interaction complexity and availability
                    unlocks = {} -- Item interaction progression unlocks and combinations
                }
            },
            battle = { -- Current battle context for interaction effects
                waveIndex = 1, -- Wave progression for interaction calculations
                conditions = {}, -- Battle conditions affecting item interactions
                activePokemon = {} -- Pokemon state for item effect applications
            }
        },
        parameters = {
            interactionType = "combination", -- combination, override, cancellation, duration
            itemIds = {"POTION", "SUPER_POTION"}, -- Items involved in interaction (matches ModifierType keys)
            targetPokemon = 0, -- Pokemon index for effect application
            statusConditions = {}, -- Current status effects for interaction timing
            durationData = {}, -- Duration tracking for temporary effects
            precedenceLevel = 1 -- Precedence level for stacking evaluation
        }
    }
}

-- Response Message Structure  
ao.send({
    Target = msg.From,
    Action = "SaveState", -- or "Error" for invalid interactions
    Success = "true",
    Operation = "calculateInteraction",
    Data = {
        interactionResult = {
            effectCombination = {
                primaryEffect = "healing", -- Main effect type
                secondaryEffects = {}, -- Additional effects from combination
                calculationOrder = {}, -- Order of effect application
                finalResult = 150, -- Calculated final effect value
                precedenceApplied = true -- Whether precedence rules were applied
            },
            stackingResult = {
                stackCount = 2, -- Number of stacked modifiers
                stackLimit = 3, -- Maximum allowed stack
                stackingAllowed = true, -- Whether additional stacking is permitted
                precedenceOrder = {} -- Order of modifier precedence
            },
            durationTracking = {
                effectDuration = 5, -- Remaining turns for temporary effects
                expirationTrigger = "turn_end", -- When effect expires
                persistentAcrossBattles = false -- Whether effect persists across battles
            },
            conflictResolution = {
                conflictDetected = false, -- Whether conflicting effects were found
                resolution = "override", -- How conflict was resolved (override, merge, cancel)
                resolvedEffect = {} -- Final effect after conflict resolution
            }
        },
        validation = {
            combinationValid = true, -- Whether item combination is valid
            timingCorrect = true, -- Whether interaction timing is correct
            precedenceCorrect = true, -- Whether precedence rules were followed
            parity = "PASS" -- Parity validation against TypeScript
        }
    }
})
```

### Technical Constraints

**Performance Requirements** [Source: architecture/tech-stack.md#performance-constraints]:
- Sub-50ms response times for item interaction calculations and complex scenario resolution
- Process size under 500KB limit (existing modifier system at 89.93KB provides headroom)
- 5-second timeout limit for complex item interaction operations from modifier system
- Memory-efficient embedded interaction database design (extend existing ModifierTypes database)

**AO Runtime Compliance** [Source: architecture/tech-stack.md#process-implementation-requirements]:
- Monolithic design with all interaction dependencies embedded in modifier-system-engine.lua
- Handler pattern using `Handlers.add()` with individual handlers for each interaction operation type
- Direct error handling patterns avoiding excessive pcall usage for interaction validation
- Deterministic execution using seeded RNG for interaction effect calculations and duration tracking

### Security Requirements

**Input Validation and Sanitization** [Source: architecture/tech-stack.md#security-and-validation]:
- All item interaction parameters must be validated for type, range, and format before processing
- GameState data integrity validation to prevent corruption during item interaction calculations
- Message authentication verification for all inter-process communication during item interactions
- Input sanitization for item IDs, quantities, and interaction parameters to prevent injection attacks

**State Integrity Protection** [Source: architecture/coding-standards.md#MANDATORY BEHAVIORAL PARITY RULES]:
- Item interaction calculations must be deterministic and reproducible using battle seeds
- All item effect modifications must maintain state consistency across battle events
- Item stacking limits must be enforced to prevent overflow or underflow conditions
- Cross-process item interaction state must be validated for consistency and authenticity

**Process Isolation and Resource Protection** [Source: architecture/tech-stack.md#security-and-validation]:
- Item interaction operations must not access system resources outside AO process sandbox
- Memory usage must be bounded to prevent resource exhaustion during complex interactions
- No external network access or file system operations during item interaction processing
- Process timeout enforcement to prevent infinite loops in item combination calculations

**Data Privacy and Access Control**:
- Item interaction data should not expose sensitive player information in error messages
- Item database access must be read-only to prevent unauthorized modification
- Battle state information must be properly scoped to prevent cross-battle data leakage
- Interaction history must not persist sensitive player behavioral patterns
