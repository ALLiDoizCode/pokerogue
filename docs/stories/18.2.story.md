**Challenge Types Implemented:**

[Source: src/enums/challenges.ts:1-12, src/data/challenge.ts:1184-1193]

1. **SINGLE_GENERATION** (maxValue: 9) - Mono-generation runs (Gen 1-9)
   - Applies: applyStarterChoice, applyPokemonInBattle, applyFixedBattle
   - Ribbon: MONO_GEN_1 through MONO_GEN_9 (bitshift based on value)

2. **SINGLE_TYPE** (maxValue: 18) - Mono-type runs (all 18 types)
   - Applies: applyStarterChoice, applyPokemonInBattle
   - Ribbon: Type-specific ribbons via bitshift

3. **FRESH_START** (maxValue: 2) - No unlocks/candies
   - Applies: applyStarterSelectModify (clears candies/passive unlocks)
   - Severity: 0 = no candies, 1 = no passive unlocks, 2 = both

4. **INVERSE_BATTLE** (maxValue: 1) - Inverted type chart
   - Applies: applyTypeEffectiveness (inverts effectiveness multipliers)
   - Ribbon: INVERSE_BATTLE

5. **FLIP_STAT** (maxValue: 1) - Flipped offensive/defensive stats
   - Applies: applyFlipStat (swaps ATK↔DEF, SPATK↔SPDEF)

6. **LOWER_MAX_STARTER_COST** (maxValue: 9) - Reduced party cost limit
   - Applies: applyStarterPoints (10 - value = max cost)
   - Value 1 = 9 cost max, Value 9 = 1 cost max

7. **LOWER_STARTER_POINTS** (maxValue: 9) - Reduced starter points
   - Applies: applyStarterPoints (10 - value = starter points)
   - Value 1 = 9 points, Value 9 = 1 point

8. **LIMITED_SUPPORT** (maxValue: 3) - Restricted support items
   - Applies: applyShop, applyShopItem, applyWaveReward
   - Severity tiers: 1 = basic items, 2 = pokeballs, 3 = all items

9. **LIMITED_CATCH** (maxValue: 1) - No catching mechanics
   - Applies: applyPokemonAddToParty (always prevents catch)

10. **HARDCORE** (maxValue: 1) - Permanent death, no revives
    - Applies: applyPokemonFusion, applyShopItem, applyWaveReward, applyPokemonMove, applyPreventRevive
    - Blocks: revive items, Revival Blessing move, fusion of fainted pokemon
    - Ribbon: HARDCORE

### API Specifications

[Source: AO Process handler pattern from tech-stack.md, challenge.ts analysis]

**Handler Specifications:**

1. **CreateChallenge** - Initialize new challenge instance
   - Input: ChallengeId (enum), Value (optional), Severity (optional)
   - Validation: Challenge ID valid, value ≤ maxValue, severity ≤ maxSeverity
   - Output: Challenge instance with default/provided values

2. **ModifyChallenge** - Adjust challenge strength/severity
   - Input: ChallengeId, Operation (enum), GameState (for validation)
   - Operations: IncreaseValue, DecreaseValue, IncreaseSeverity, DecreaseSeverity, Reset
   - Validation: Operation within bounds (0 ≤ value ≤ maxValue, etc.)
   - Output: Updated challenge instance, success boolean

3. **ValidateChallenge** - Check unlock conditions
   - Input: ChallengeId, GameState (save data with progression)
   - Validation: All conditions met (e.g., beat game, unlock specific achievements)
   - Output: Boolean unlocked status, failed conditions list

4. **GetChallengeInfo** - Query challenge metadata
   - Input: ChallengeId (optional, omit for all)
   - Output: Challenge metadata (name, description, maxValue, maxSeverity, ribbonAwarded, i18nKey)

5. **ApplyChallengeHook** - Execute challenge logic hooks
   - Input: Hook name, ChallengeId, Hook-specific parameters (BooleanHolder, NumberHolder, etc.)
   - Validation: Hook exists for challenge type, parameters valid
   - Output: Modified parameters (e.g., valid.value = false, points.value -= 5)

6. **SerializeChallenge** - Export challenge state
   - Input: ChallengeId
   - Output: ChallengeData {id, value, severity}

7. **DeserializeChallenge** - Import challenge state
   - Input: ChallengeData {id, value, severity}
   - Validation: Valid challenge ID, values within bounds
   - Output: Challenge instance

8. **GetActiveChallenges** - Query active challenge configuration
   - Input: GameState (player save data)
   - Output: Array of active ChallengeData instances

### Technical Constraints

[Source: docs/architecture/tech-stack.md:28-91]

**AO Runtime Specifications:**
- **Execution Timeout**: 5-second limit per message handler
- **File Size Limit**: 500KB maximum per process file
- **Memory Constraints**: Limited by AO network specifications
- **CPU Cycles**: Bounded computational resources per execution
- **Message Size**: Practical limits on JSON payload size

**Process Implementation Requirements:**
- **Monolithic Design**: All dependencies embedded in single file, no require() statements (except require("json"))
- **Handler Pattern**: Use `Handlers.add()` with tag matching, not direct assignment
- **Error Handling**: Direct error handling with ao.send() and return statements (avoid unnecessary pcall)
- **Performance Monitoring**: Built-in timeout detection and execution time tracking
- **Deterministic Execution**: Seeded RNG, no process-local randomness or external I/O
- **Timestamp Handling**: Use msg.Timestamp instead of os.time()

**Available AO Globals:**
- `ao.send()` - Message transmission to other processes
- `ao.id` - Process identifier for debugging metadata
- `Handlers` - Message routing via Handlers.add(name, matcher, handler)
- `json` - Data serialization (encode/decode message data and GameState objects)
- Standard Lua: string, table, math, os (limited subset)

**Security and Validation:**
- **Input Sanitization**: All external data validated and sanitized
- **Deterministic Behavior**: No access to system time (use msg.Timestamp), filesystem, or network
- **Process Isolation**: Each process runs in isolated Lua environment
- **Message Authentication**: AO protocol handles cryptographic verification
- **State Integrity**: GameState validation prevents corruption across processes

### Architecture-Informed Implementation Notes

**Challenge Type Implementation Strategy:**

[Source: src/data/challenge.ts:447-1148]

Each challenge type requires:
1. **Class Definition**: Extend base Challenge class
2. **Constructor**: Set id, maxValue, maxSeverity
3. **Hook Overrides**: Implement relevant apply* methods
4. **ribbonAwarded Logic**: Calculate ribbon flag (bitshift for series, static for single)
5. **loadChallenge Method**: Static method for deserialization

**Lua Implementation Pattern:**
```lua
-- Factory function for each challenge type
local function createSingleGenerationChallenge()
    return {
        id = 0,  -- Challenges.SINGLE_GENERATION
        value = 0,
        maxValue = 9,
        severity = 0,
        maxSeverity = 0,

        getRibbonAwarded = function(self)
            -- Bitshift logic: MONO_GEN_1 << (value - 1)
            return self.value > 0 and (1 << (self.value - 1)) or 0
        end,

        applyStarterChoice = function(self, pokemon, valid)
            if pokemon.generation ~= self.value then
                valid.value = false
                return true
            end
            return false
        end,

        -- Additional hooks...
    }
end
```

**BooleanHolder/NumberHolder Pattern:**

[Source: TypeScript analysis, AO Lua translation patterns]

TypeScript uses mutable objects for pass-by-reference modification:
```typescript
type BooleanHolder = { value: boolean }
type NumberHolder = { value: number }

// Hook modifies holder in-place
applyStarterChoice(pokemon: PokemonSpecies, valid: BooleanHolder): boolean {
    if (pokemon.generation !== this.value) {
        valid.value = false  // Modify holder
        return true          // Signal modification occurred
    }
    return false             // No modification
}
```

Lua equivalent:
```lua
-- Caller creates holder table
local valid = {value = true}
local modified = challenge:applyStarterChoice(pokemon, valid)
if modified then
    -- Check valid.value for result
end
```

**Unlock Condition Pattern:**

[Source: src/data/challenge.ts:92-105]

Challenges can have unlock conditions (functions taking GameData):
```typescript
isUnlocked(data: GameData): boolean {
    return this.conditions.every(f => f(data));
}

condition(condition: ChallengeCondition): Challenge {
    this.conditions.push(condition);
    return this;  // Chainable
}
```

Lua equivalent:
```lua
local function isUnlocked(self, gameData)
    for _, conditionFn in ipairs(self.conditions) do
        if not conditionFn(gameData) then
            return false
        end
    end
    return true
end

local function addCondition(self, conditionFn)
    table.insert(self.conditions, conditionFn)
    return self  -- Chainable
end
```

### AO Compliance Requirements

[Source: CLAUDE.md:114-287, docs/architecture/ao-compliance-guidelines.md]

**CRITICAL Compliance Patterns:**

1. **No External Dependencies** (except require("json"))
   ```lua
   -- ✅ CORRECT: Embedded challenge factory functions
   local function createSingleGenerationChallenge() ... end

   -- ❌ FORBIDDEN: External requires
   local challengeUtils = require("challenge-utils")
   ```

2. **Direct Error Handling** (avoid unnecessary pcall)
   ```lua
   -- ✅ CORRECT: Direct validation with error response
   if not msg.ChallengeId then
       ao.send({Target = msg.From, Action = "Error", Error = "ChallengeId required"})
       return
   end

   -- ❌ FORBIDDEN: Unnecessary pcall wrapper
   local success, result = pcall(function()
       return createChallenge(msg.ChallengeId)
   end)
   ```

3. **Handler Pattern** (use Handlers.add)
   ```lua
   -- ✅ CORRECT: Individual handler per action
   Handlers.add("create-challenge",
       Handlers.utils.hasMatchingTag("Action", "CreateChallenge"),
       function(msg) ... end
   )

   -- ❌ FORBIDDEN: Direct assignment
   Handlers["CreateChallenge"] = function(msg) ... end
   ```

4. **Timestamp Handling** (use msg.Timestamp)
   ```lua
   -- ✅ CORRECT: Use message timestamp
   local timestamp = msg.Timestamp or 0

   -- ❌ FORBIDDEN: os.time() in AO processes
   local timestamp = os.time()
   ```

5. **Tags vs Data Field Usage**
   ```lua
   -- ✅ CORRECT: Simple parameters in tags
   local challengeId = tonumber(msg.ChallengeId)
   local operation = msg.Operation

   -- ✅ CORRECT: Complex structures in Data field
   local hookParams = json.decode(msg.Data or "{}")

   -- ❌ FORBIDDEN: Simple data in Data field
   local data = json.decode(msg.Data or "{}")
   local challengeId = data.id  -- Should be msg.ChallengeId tag
   ```

6. **Response Format** (all tag values as strings)
   ```lua
   -- ✅ CORRECT: String values for all tags
   ao.send({
       Target = msg.From,
       Action = "SaveState",
       ChallengeId = tostring(challengeId),
       Value = tostring(challenge.value),
       Severity = tostring(challenge.severity),
       RibbonAwarded = tostring(challenge:getRibbonAwarded())
   })

   -- ❌ FORBIDDEN: Non-string tag values
   ao.send({
       Target = msg.From,
       ChallengeId = challengeId,  -- Number, should be string
       Value = challenge.value      -- Number, should be string
   })
   ```

7. **ADP v1.0 Compliance** (required Info handler)
   ```lua
   Handlers.add("info",
       Handlers.utils.hasMatchingTag("Action", "Info"),

           ao.send({
               Target = msg.From,
   ```

### Coding Standards

[Source: docs/architecture/coding-standards.md:1-21]

**Naming Conventions:**
- **Functions**: camelCase - `createChallenge()`, `applyStarterChoice()`
- **Variables**: camelCase - `challengeId`, `hookResult`
- **Constants**: UPPER_SNAKE_CASE - `MAX_CHALLENGE_VALUE`, `CHALLENGES_ENUM`
- **Tables/Objects**: PascalCase - `Challenge`, `ChallengeData`
- **Files**: kebab-case - `challenge-framework-engine.lua`

**Mandatory Behavioral Parity Rules:**
- Never use Lua's math.random() - ALWAYS use AO crypto module (if randomness needed)
- All calculations must match TypeScript Math.floor/Math.ceil exactly
- Challenge difficulty multipliers must be exact (no approximations)
- All AO message responses must include success indicators (Action = "SaveState" or "Error")
- Never hardcode challenge data - always reference embedded tables
- Challenge value/severity must be validated on every modification
