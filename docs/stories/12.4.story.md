### Terastalization Battle Integration Analysis

#### Core Battle Integration Components [Source: TypeScript codebase analysis and previous stories]

**1. Battle Timing and Activation Sequence**
- **Terastalization Activation**: Must occur during battle turn before move selection, similar to Mega Evolution timing
- **Usage Limitation**: One Terastallization per battle per Pokemon, tracked in `battleData.teraUsed` 
- **Prerequisite Validation**: Requires Tera Orb (global unlock) and appropriate battle conditions
- **Turn Priority**: Terastallization occurs immediately, doesn't consume turn action

**2. Battle State Integration**
- **Battle Phase Integration**: Terastallization occurs during "COMMAND_PHASE" before "MOVE_EXECUTION_PHASE"
- **State Persistence**: Tera type changes persist for entire battle duration
- **Cross-Turn Effects**: Tera type affects all subsequent damage calculations, status effects, and interactions

**3. Status Effect Interactions**
- **Type-Based Status Immunity**: Tera type change can grant immunity to certain status effects (e.g., Fire type immunity to burn)
- **Existing Status Preservation**: Current status effects remain active during Tera transformation
- **Status Application Priority**: New status effects check against current Tera type, not original types

**4. Weather and Terrain Interactions**
- **Weather Effect Calculation**: Tera type affects weather damage/healing (e.g., Fire type in hail)
- **Terrain Effect Priority**: Tera type determines terrain effectiveness (e.g., Electric Terrain + Electric Tera type)
- **Field Effect Stacking**: Tera type modifies field effect interactions and priority resolution

**5. AI Decision Making Integration**
- **Move Selection Logic**: AI must consider opponent's potential Tera type changes
- **Type Prediction**: AI should factor Tera type possibilities in damage calculations
- **Counter-Strategy**: AI should adjust strategy based on player's Tera usage patterns

### Process Coordination Architecture

#### Cross-Process Communication Pattern
```lua
-- Coordination with existing Tera processes
local function coordinateWithTeraProcesses(battleData)
    -- 1. Validate with tera-type-engine.lua
    local teraValidation = ao.send({
        Target = TERA_TYPE_PROCESS_ID,
        Action = "ValidateTeraActivation",
        Data = json.encode({
            pokemonId = battleData.pokemonId,
            requestedType = battleData.teraType,
            battleContext = battleData.battleState
        })
    })
    
    -- 2. Update tera-crystal-engine.lua usage tracking
    ao.send({
        Target = TERA_CRYSTAL_PROCESS_ID,
        Action = "ProcessTeraCrystal",
        Operation = "consume",
        Data = json.encode({
            playerId = battleData.playerId,
            usageType = "BATTLE_ACTIVATION",
            battleId = battleData.battleId
        })
    })
    
    -- 3. Coordinate with stellar-tera-engine.lua if applicable
    if battleData.teraType == "STELLAR" then
        ao.send({
            Target = STELLAR_TERA_PROCESS_ID,
            Action = "ProcessStellarTera",
            Operation = "battleActivation",
            Data = json.encode(battleData)
        })
    end
end
```

### Technical Constraints [Source: architecture/tech-stack.md]

**AO Runtime Requirements**:
- **Monolithic Design**: All dependencies embedded in single file, no require() statements
- **Handler Pattern**: Use `Handlers.add()` with tag matching, not direct assignment  
- **Error Handling**: Direct error handling with ao.send() responses, avoid unnecessary pcall usage
- **Performance**: 5-second execution timeout, 500KB file size limit
- **Deterministic Execution**: Use msg.Timestamp, no os.time() or math.random()

**Available AO Globals**:
- `ao.send()` - Message transmission to other processes
- `ao.id` - Process identifier  
- `Handlers` - Message routing system
- `json` - Data serialization for cross-process communication
- Standard Lua: string, table, math (limited subset)

### Security and Validation Requirements [Source: architecture/coding-standards.md]

**Mandatory Behavioral Parity Rules**:
- Never use Lua's math.random() - ALWAYS use AO crypto module for deterministic randomness
- All stat calculations must match TypeScript Math.floor/Math.ceil exactly
- Nature multipliers must be exactly 0.9, 1.0, or 1.1 - never approximate
- All AO message responses must include success boolean
- Never hardcode Pokemon/Move/Item data - always reference database tables
- Battle RNG counter must increment for every random call

**Input Validation**:
- All external data validated and sanitized
- Battle state consistency verification  
- Cross-process message validation
- Pokemon state integrity checks
