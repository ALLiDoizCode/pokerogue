## Story Statement
As a **unlockable content engineer**,
I want **unlockable content systems migrated to stateless AO process**,
so that **content unlocking and availability maintain identical trigger conditions and access behavior**.

## Acceptance Criteria
1. Content unlock condition evaluation maintains identical trigger logic and threshold determination
2. Unlock progression tracking maintains identical milestone detection and completion logging
3. Content availability validation maintains identical access control and restriction enforcement
4. Unlock reward distribution maintains identical calculation and allocation behavior
5. Content unlock persistence maintains identical state tracking across save/load operations
6. Unlock notification systems maintain identical messaging and presentation behavior
7. Complex unlock dependency chains maintain identical sequence logic and completion validation
8. Comprehensive testing validates 100% unlockable content system behavioral and logical parity

## Dev Notes

### Previous Story Insights
- Story 15.1 completed Passive Ability System Migration with `passive-ability-engine.lua` handling passive triggers, unlock/upgrade mechanics, and battle coordination
- Critical lessons from Story 15.1:
  - Monolithic design with all dependencies embedded (no require() statements except json)
  - Error handling: Direct validation with ao.send() error responses, avoid unnecessary pcall (only for genuinely unpredictable operations like external JSON parsing)
  - Proper AO message coordination between processes using ao.send() with structured Target, Action, Data
  - Process size targets: 10-15KB for simple logic processes, 35-45KB for complex logic, 70-80KB for large embedded data (well within 500KB limit)
  - ADP v1.0 compliance required with Info handler for self-documentation
  - Tag-based message parameters for simple values, Data field for complex structures
  - Avoid module-level returns - use message passing exclusively
  - All tag values MUST be strings: tostring(number), "true"/"false" for booleans
  - Timestamp handling: CRITICAL - Use msg.Timestamp, NEVER os.time() (AO runtime requirement)
- **DISCOVERY**: Unlockable content system is much simpler than passive abilities:
  - Only 4 unlockables in TypeScript implementation: ENDLESS_MODE, MINI_BLACK_HOLE, SPLICED_ENDLESS_MODE, EVIOLITE
  - Unlock conditions are game mode completion triggers (Classic victory for all)
  - State tracked in player game data as simple boolean flags
  - No complex calculations or battle integration required
- **REFERENCE SOURCE**: TypeScript implementation contains minimal files for unlockables:
  - `typescript-reference/src/enums/unlockables.ts` - 4 unlockable enums (8 lines)
  - `typescript-reference/src/system/unlockables.ts` - Name mapping function (18 lines)
  - `typescript-reference/src/phases/unlock-phase.ts` - Unlock notification phase (40 lines)
  - `typescript-reference/src/phases/game-over-phase.ts` - Unlock trigger logic (handleUnlocks method, lines 287-308)
  - `typescript-reference/src/system/game-data.ts` - Unlock state storage (unlocks object, lines 254, 273-278)
- **PARITY APPROACH**: All unlock trigger conditions must match TypeScript behavior exactly including Classic victory detection, fusion check for SPLICED_ENDLESS_MODE, evolution check for EVIOLITE
- Testing validation patterns: Unit tests with aolite, integration tests with aos-local, parity tests against TypeScript, AO sandbox compliance validation

##### Check Unlock Status
```lua

    Action = "IsUnlocked",
    PlayerId = "player_address",

    Target = msg.From,
```

### Coordinator Integration Sequences
#### Unlock Evaluation on Game Victory Workflow
```lua
-- Step 1: Game completion detected (from game-over-phase)
ClientRequest -> coordinator-process {
    Action = "GameOver",
    PlayerId = "player_456",
    GameMode = "classic",
    IsVictory = "true",
    PartyData = {...}
}

-- Step 2: Coordinator requests unlock evaluation
coordinator-process -> unlockable-content-engine {
    Action = "EvaluateUnlocks",
    PlayerId = "player_456",
    GameMode = "classic",
    IsVictory = "true",
    PartyData = json.encode({
        hasFusion = true,
        hasUnevolved = false,
        partySize = 6
    })
}

-- Step 3: Unlock engine evaluates conditions
unlockable-content-engine -> coordinator-process {
    Action = "UnlockEvaluationResult",
    Data = json.encode({
        newUnlocks = {
            { unlockableId = 0, name = "Endless Mode" },
            { unlockableId = 1, name = "Mini Black Hole" },
            { unlockableId = 2, name = "Spliced Endless Mode" }
        },
        totalUnlocked = 3
    })
}

-- Step 4: Coordinator stores unlock state
coordinator-process -> player-progression-engine {
    Action = "UpdatePlayerUnlocks",
    PlayerId = "player_456",
    UnlockData = json.encode({...})
}

-- Step 5: State persistence confirmation
player-progression-engine -> coordinator-process {
    Action = "UnlocksUpdated",
    Success = "true"
}

-- Step 6: Coordinator triggers notifications
coordinator-process -> notification-engine {
    Action = "ShowUnlockNotifications",
    PlayerId = "player_456",
    NewUnlocks = json.encode([...])
}

-- Step 7: Return to client with results
coordinator-process -> Client {
    Action = "GameOverComplete",
    Data = json.encode({
        victory = true,
        newUnlocks = 3,
        unlockNotifications = [...]
    })
}
```

### Technical Constraints
[Source: architecture/tech-stack.md, CLAUDE.md]
- **Execution Timeout**: 5-second limit per message handler
- **File Size Limit**: 500KB maximum per process file (target 10-15KB for simple unlockables)
- **Monolithic Design**: All dependencies embedded, no external imports except json
- **Handler Pattern**: Use Handlers.add() with tag matching, not direct assignment
- **Message Protocol**: JSON-encoded data with structured ao.send() responses
- **Timestamp Handling**: CRITICAL - Use msg.Timestamp, NEVER os.time() (AO runtime requirement - os.time() will fail AO sandbox validation)
- **Error Handling**: Direct validation with ao.send() error responses, avoid unnecessary pcall (only for genuinely unpredictable operations)
- **Small Data Structure**: Only 4 unlockables - minimal embedded data needed
- **Tag Values**: All tag values MUST be strings: tostring(number), "true"/"false" for booleans

### Security Requirements
- **Input Validation**: All player IDs and unlockable IDs must be validated before processing
- **Authorization**: Player can only query/modify their own unlock state (verify msg.From matches PlayerId for state mutations)
- **Force Unlock Protection**: ForceUnlock flag implementation deferred - if needed, coordinator should validate admin privileges before sending GrantUnlock with ForceUnlock="true"
- **State Integrity**: Ensure unlock state cannot be corrupted or exploited
- **Victory Validation**: Verify game mode and victory conditions before granting unlocks
- **Idempotency**: Multiple unlock grant calls for same unlockable should be safe (already unlocked = no-op)
