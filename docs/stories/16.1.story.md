# Story 16.1: Biome Progression Migration

**Epic:** Epic 16 - World Progression & Biome System
**Status:** Done
**Created:** October 1, 2025
**Assigned:** Biome System Engineering Team

## Story Statement
As a **biome system engineer**,
I want **biome progression and unlocking systems migrated to stateless AO process**,
so that **world area advancement maintains identical progression logic and availability behavior**.

## Acceptance Criteria
1. Biome unlock condition evaluation maintains identical progression trigger logic and requirement validation
2. Biome progression tracking maintains identical milestone detection and advancement calculation
3. Biome availability validation maintains identical access control and restriction enforcement
4. Biome transition mechanics maintain identical zone change logic and state persistence
5. Complex biome dependency chains maintain identical sequence logic and completion validation
6. Biome depth calculation maintains identical graph traversal and weighted probability logic
7. Comprehensive testing validates 100% biome progression system behavioral and logical parity

**OUT OF SCOPE** (Handled by other processes/stories):
- AC4 (Environmental Effects): Weather/terrain effects handled by battle-engine and arena management
- AC6 (Progression Rewards): Money/healing rewards handled by reward-engine and party-management

## Dev Notes

### Previous Story Insights
- Story 15.4 completed Voucher Reward System Migration with 22.27KB process achieving 100% test coverage (36/36 passing)
- Epic 15 (Passive Abilities & Unlockables) established: ability effects, nature modifiers, achievement tracking, voucher systems
- Key lessons from Stories 15.1-15.4:
  - Monolithic design with all dependencies embedded (no require() except json)
  - Error handling: Direct validation with ao.send() error responses, avoid unnecessary pcall
  - Proper AO message coordination using ao.send() with structured Target, Action, Data
  - Process size targets: 10-15KB for simple processes, 35-45KB for complex logic, 70-80KB for large embedded data
  - ADP v1.0 compliance required with Info handler for self-documentation
  - Tag-based message parameters for simple values, Data field for complex structures
  - Avoid module-level returns - use message passing exclusively
  - All tag values MUST be strings: tostring(number), "true"/"false" for booleans
  - Timestamp handling: CRITICAL - Use msg.Timestamp, NEVER os.time()
- **COMPLEXITY ASSESSMENT**: Biome system is moderately complex with rich graph-based progression:
  - 36 total biomes (BiomeId enum: TOWN through LABORATORY, plus END at 50)
  - Graph-based progression with biomeLinks mapping (not linear progression)
  - Probabilistic biome selection with weighted alternatives: [BiomeId, weight] tuples
  - Biome depth calculation via recursive graph traversal for random biome weighting
  - Multiple progression paths from each biome (1-3 possible next biomes)
  - Special biome selection logic: Map modifier enables player choice between available biomes
  - Boss battle milestones: Every 10 waves triggers biome transition opportunity
  - END biome special handling: Wave 50 terminus in Classic mode
- **TIME OF DAY (ToD) OUT OF SCOPE**: ToD affects Pokemon pool selection and encounter rates but is handled by encounter-engine and pokemon-pool-manager processes, not biome progression. This story focuses solely on biome selection and transition mechanics.
- **REFERENCE SOURCE**: TypeScript implementation across multiple files:
  - `typescript-reference/src/enums/biome-id.ts` - BiomeId enum (36 biomes + END)
  - `typescript-reference/src/data/balance/biomes.ts` - biomeLinks, biomeDepths, BiomePoolTier, biomePokemonPools, biomeTrainerPools (329KB file)
  - `typescript-reference/src/phases/select-biome-phase.ts` - Biome selection logic (90 lines)
  - `typescript-reference/src/phases/switch-biome-phase.ts` - Biome transition execution (71 lines)
  - `typescript-reference/src/field/arena.ts` - Arena initialization, Pokemon/trainer pool management, time of day updates
- **PARITY APPROACH**: All biome progression rules, weighted selection, and transition logic must match TypeScript exactly
- **DATA EMBEDDING STRATEGY**: 329KB biomes.ts contains Pokemon/trainer pools (OUT OF SCOPE). This story embeds:
  - biomeLinks structure (36 entries, ~2KB) - REQUIRED for progression
  - BiomeId enum (36 biomes, ~500 bytes) - REQUIRED for progression
  - biomeDepths calculation algorithm (traverseBiome function) - REQUIRED for random biome generation
  - Pokemon pools and trainer pools are NOT embedded (handled by pokemon-pool-manager and trainer-encounter-engine)
  - Expected process size: 10-15KB (biome logic + embedded graph data)
- Testing validation patterns: Unit tests with aolite, integration tests with aos-local, parity tests against TypeScript

#### Biome Depth Model
[Source: typescript-reference/src/data/balance/biomes.ts#L7601-7628]
```lua
-- Biome depth calculation: [minDepth, biomeChance] for progression weighting
-- Calculated via recursive graph traversal from TOWN (depth 0)
-- Used for random biome generation weighted selection
local biomeDepths = {
    [BiomeId.TOWN] = {0, 1},  -- Starting biome
    -- Populated dynamically by traverseBiome function:
    -- 1. Start from TOWN at depth 0
    -- 2. For each linked biome, record depth+1 and biomeChance
    -- 3. If biome has multiple paths, record shortest depth with lowest chance
    -- 4. END biome depth = max(all depths) + 1
    -- Example results: [BiomeId.PLAINS] = {1, 1}, [BiomeId.GRASS] = {2, 1},
    --                  [BiomeId.SWAMP] = {3, 2} (reached via weighted link)
}
```

#### Process Message Interface

##### Select Next Biome
[Source: NEW FOR AO - Based on typescript-reference/src/phases/select-biome-phase.ts#L14-88]
```lua
-- Incoming: Select next biome for progression
msg = {
    Action = "SelectNextBiome",
    PlayerId = "player_address",
    CurrentBiome = "1",  -- BiomeId.PLAINS
    CurrentWaveIndex = "25",
    GameMode = "classic",  -- "classic", "daily", or mode-specific flags
    HasMapModifier = "false",  -- "true" if player has Map modifier item
    From = "sender_address"
}

-- Outgoing: Next biome selection result
ao.send({
    Target = msg.From,
    Action = "BiomeSelected",
    PlayerId = msg.PlayerId,
    NextBiome = "3",  -- BiomeId.TALL_GRASS
    AvailableBiomes = json.encode({3, 13}),  -- If HasMapModifier=true, show options
    NextWaveIndex = "30",
    RequiresPlayerChoice = "false",  -- "true" if multiple biomes and Map modifier
    TransitionType = "standard",  -- "standard", "end_biome", "random"
    Timestamp = tostring(msg.Timestamp)
})
```

#### Standard Biome Selection Workflow
[Source: typescript-reference/src/phases/select-biome-phase.ts]
```lua
-- Step 1: Wave milestone reached (every 10 waves)
ClientRequest -> coordinator-process {
    Action = "CheckBiomeTransition",
    PlayerId = "player_456",
    CurrentWaveIndex = "29"  -- Wave 30 approaching
}

-- Step 2: Coordinator queries current biome state
coordinator-process -> biome-progression-engine {
    Action = "GetPlayerBiomeState",
    PlayerId = "player_456"
}

-- Step 3: Biome state returned
biome-progression-engine -> coordinator-process {
    Action = "PlayerBiomeData",
    Data = json.encode({
        currentBiome = 1,  -- PLAINS
        currentWaveIndex = 29
    })
}

-- Step 4: Coordinator requests next biome selection
coordinator-process -> biome-progression-engine {
    Action = "SelectNextBiome",
    PlayerId = "player_456",
    CurrentBiome = "1",  -- PLAINS
    CurrentWaveIndex = "30",
    HasMapModifier = "false",
    GameMode = "classic"
}

-- Step 5: Biome selection result
biome-progression-engine -> coordinator-process {
    Action = "BiomeSelected",
    NextBiome = "3",  -- TALL_GRASS (random from GRASS, METROPOLIS, LAKE)
    RequiresPlayerChoice = "false"
}

-- Step 6: Execute biome transition
coordinator-process -> biome-progression-engine {
    Action = "ExecuteBiomeTransition",
    PlayerId = "player_456",
    FromBiome = "1",
    ToBiome = "3",
    WaveIndex = "30"
}

-- Step 7: Transition complete
biome-progression-engine -> coordinator-process {
    Action = "BiomeTransitioned",
    NewBiome = "3",
    BiomeName = "Tall Grass",
    FirstVisit = "true"
}

-- Step 8: Update player progression state
coordinator-process -> player-progression-engine {
    Action = "UpdateBiomeState",
    PlayerId = "player_456",
    BiomeData = json.encode({
        currentBiome = 3,
        unlockedBiomes = {...},
        biomeHistory = {...}
    })
}

-- Step 9: Return to client with biome change
coordinator-process -> Client {
    Action = "BiomeTransitionComplete",

        newBiome = 3,
        biomeName = "Tall Grass",
        firstVisit = true
    })
}
```

### Technical Constraints
[Source: architecture/tech-stack.md]
- **Execution Timeout**: 5-second limit per message handler
- **File Size Limit**: 500KB maximum per process file (target 10-15KB for biome progression logic)
- **Monolithic Design**: All biome metadata embedded, no external imports except json
- **Handler Pattern**: Use Handlers.add() with tag matching, not direct assignment
- **Message Protocol**: JSON-encoded data with structured ao.send() responses
- **Timestamp Handling**: CRITICAL - Use msg.Timestamp, NEVER os.time()
- **Error Handling**: Direct validation with ao.send() error responses, avoid unnecessary pcall
- **Tag Values**: All tag values MUST be strings: tostring(number), "true"/"false" for booleans
- **Biome Graph Data**: Requires embedded biomeLinks structure (36 biomes, ~2KB) and biomeDepths calculation
- **Seeded Randomness**: Use deterministic RNG for biome selection (passed in messages)
- **Data Scope**: ONLY biome progression data - Pokemon/trainer pools excluded (separate processes)

### Security Requirements
- **Input Validation**: All player IDs and biome IDs must be validated before processing
- **Authorization**: Player can only query/modify their own biome state
- **State Integrity**: Ensure biome unlock timestamps cannot be forged or manipulated
- **Progression Validation**: Biome transitions must follow biomeLinks rules (no arbitrary jumps)
- **Wave Milestone Validation**: Biome transitions only allowed at milestone waves (10, 20, 30...)
- **Choice Validation**: If Map modifier present, player choice must be from available links
- **END Biome Protection**: END biome selection enforced at wave 50 in Classic mode

- Following established pattern from Epic 15 Stories 15.1-15.4
- New process file aligns with existing progression system processes

- **PROCESS SIZE ESTIMATE**: 10-15KB target (2-3% of 500KB limit) for biome progression logic
- **DATA EXCLUSIONS**: Pokemon pools, trainer pools, encounter rates NOT included (separate processes)
