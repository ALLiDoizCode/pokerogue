## Story Statement
As a **battle system engineer**,  
I want **core turn-based battle mechanics migrated to stateless AO process**,  
so that **battle flow and turn resolution produce identical outcomes to TypeScript implementation**.

## Acceptance Criteria
1. Turn order calculation maintains identical priority rules and speed tie-breaking
2. Action selection and validation ensures identical move availability and constraints
3. Turn execution sequence maintains identical timing for abilities, items, and status effects
4. Battle state transitions (turn start/end, phase changes) execute identically to TypeScript
5. Multi-target move resolution maintains identical target selection and damage distribution
6. Switch/substitution mechanics maintain identical timing and state transitions
7. Battle flow control ensures identical handling of interrupts and priority changes
8. Comprehensive testing validates 100% turn resolution parity across all battle scenarios

### API Specifications
**Handler Message Schemas** (to be implemented):

```lua
-- CalculateTurnOrder Handler
Request: {
  Action = "CalculateTurnOrder",
  BattleId = "string",
  Participants = "string", -- JSON array of Pokemon with stats
  PriorityMoves = "string", -- JSON object of priority modifications
  Timestamp = "number"
}
Response: {
  Action = "SaveState",
  Data = {
    turnOrder = {}, -- Array of Pokemon IDs in execution order
    priorities = {}, -- Priority values for each participant
    speedValues = {} -- Speed stats used for tie-breaking
  },
  ProcessId = "string",
  Timestamp = "string"
}

-- ExecuteTurn Handler
Request: {
  Action = "ExecuteTurn",
  BattleId = "string",
  TurnData = "string", -- JSON with turn commands and participants
  BattleState = "string", -- Current battle state JSON
  Timestamp = "number"
}
Response: {
  Action = "SaveState",
  Data = {
    turnResults = {}, -- Array of action results in execution order
    battleState = {}, -- Updated battle state
    nextTurn = "number", -- Next turn number
    battleEnd = "boolean" -- Whether battle has ended
  },
  ProcessId = "string",
  Timestamp = "string"
}

-- ValidateAction Handler
Request: {
  Action = "ValidateAction",
  BattleId = "string",
  PokemonId = "string",
  ActionType = "string", -- "FIGHT", "SWITCH", "ITEM", "RUN"
  ActionData = "string", -- JSON with move/item/target data
  Timestamp = "number"
}
Response: {
  Action = "SaveState",
  Data = {
    valid = "boolean",
    availableActions = {}, -- List of valid actions
    constraints = {}, -- Active constraints affecting actions
    errors = {} -- Validation error messages if invalid
  },
  ProcessId = "string",
  Timestamp = "string"
}
```

### Technical Constraints
**Coding Standards** [Source: architecture/coding-standards.md]:
- Never use Lua's math.random() - ALWAYS use AO crypto module for deterministic battles
- All turn order calculations must match TypeScript precision exactly
- Battle RNG counter must increment for every random call to maintain deterministic replay
- All AO message responses must include success boolean
- Turn execution timing must match TypeScript exactly

**Performance Constraints** [Source: architecture/tech-stack.md#Performance Constraints]:
- Execution Timeout: 5-second limit per message handler
- File Size Limit: 500KB maximum per process file
- Memory Constraints: Limited by AO network specifications
- Message Size: Practical limits on JSON payload size for battle state

**AO Runtime Specifications** [Source: architecture/tech-stack.md#AO Runtime Specifications]:
- Monolithic Design: All dependencies embedded in single file
- Handler Pattern: Use `Handlers.add()` with tag matching
- Available globals: `ao.send()`, `ao.id`, `Handlers`, `json`
- No `require()` statements allowed

### Security Requirements
1. **Input Validation**: All battle commands and Pokemon data must be validated for legal ranges
2. **Deterministic Battles**: All randomness must use AO crypto module with battle seeds
3. **State Integrity**: Turn execution must be atomic to prevent partial battle state corruption
4. **Access Control**: Battle commands should be validated against player ownership
5. **Rate Limiting**: Handle rapid turn execution requests without memory leaks
6. **Battle Replay**: Maintain complete determinism for battle replay functionality
7. **Anti-Cheat**: Validate all battle actions against game rules to prevent exploitation

### Critical Implementation Notes
**From Architecture Analysis**:
- Turn order based on speed stats with priority move handling (+1 to +5 priority levels)
- Speed tie-breaking uses deterministic randomization (not true random)
- Multi-target moves deal reduced damage (typically 0.75x) to multiple targets
- Switch timing occurs before move execution unless forced by moves like Roar
- Battle phases: TURN_START → ACTION_SELECTION → TURN_EXECUTION → TURN_END
- Status effects and abilities have specific timing within turn execution
- Priority interrupts can change action order mid-turn (flinching, sleep, etc.)

**ADP v1.0 Compliance Requirements**:
