# Story 15.4: Voucher Reward System Migration

**Epic:** Epic 15 - Passive Abilities & Unlockables
**Status:** Done
**Created:** September 30, 2025
**Assigned:** Voucher System Engineering Team

## Story Statement
As a **voucher system engineer**,
I want **voucher reward systems migrated to stateless AO process**,
so that **egg voucher distribution and management maintain identical award conditions and inventory tracking**.

## Acceptance Criteria
1. Voucher award condition evaluation maintains identical trigger logic for achievements and boss trainer victories
2. Voucher type calculation maintains identical tier determination based on achievement scores and trainer types
3. Voucher inventory tracking maintains identical count management and persistence across sessions
4. Voucher unlock state tracking maintains identical timestamp recording and validation behavior
5. Voucher availability validation maintains identical redemption checking and constraint enforcement
6. Voucher integration with egg gacha maintains identical purchasing and consumption behavior
7. Complex voucher reward scenarios maintain identical multi-voucher award and event-based distribution
8. Comprehensive testing validates 100% voucher system behavioral and calculation parity

## Dev Notes

### Previous Story Insights
- Story 15.3 completed Achievement-Based Progression Migration with `achievement-engine.lua` handling 68 achievements with validation
- Critical lessons from Stories 15.1-15.3:
  - Monolithic design with all dependencies embedded (no require() statements except json)
  - Error handling: Direct validation with ao.send() error responses, avoid unnecessary pcall
  - Proper AO message coordination using ao.send() with structured Target, Action, Data
  - Process size targets: 10-15KB for simple processes, 35-45KB for complex logic, 70-80KB for large embedded data
  - ADP v1.0 compliance required with Info handler for self-documentation
  - Tag-based message parameters for simple values, Data field for complex structures
  - Avoid module-level returns - use message passing exclusively
  - All tag values MUST be strings: tostring(number), "true"/"false" for booleans
  - Timestamp handling: CRITICAL - Use msg.Timestamp, NEVER os.time()
- **COMPLEXITY ASSESSMENT**: Voucher system is simpler than achievements but requires tight integration:
  - Only 4 voucher types: REGULAR, PLUS, PREMIUM, GOLDEN

  - Achievement-based vouchers: Single voucher type (CLASSIC_VICTORY achievement score 250 = GOLDEN tier)
  - Boss trainer vouchers: Dynamic voucher generation based on trainer configurations
  - State tracking: voucherUnlocks (awarded vouchers with timestamps) and voucherCounts (current inventory)
  - Integration points: achievement-engine (for award triggers), egg-gacha (for consumption)

#### Voucher Initialization Logic
[Source: typescript-reference/src/system/voucher.ts#L91-123]
```lua
-- Achievement-based voucher generation
local function initAchievementVouchers()
    local achievementVouchers = {}

    -- Currently only CLASSIC_VICTORY awards voucher
    local classicVictory = achievements["CLASSIC_VICTORY"]  -- score = 250

    -- Tier calculation based on achievement score
    local voucherType
    if classicVictory.score >= 150 then
        voucherType = VoucherType.GOLDEN   -- score 250 = GOLDEN
    elseif classicVictory.score >= 100 then
        voucherType = VoucherType.PREMIUM
    elseif classicVictory.score >= 75 then
        voucherType = VoucherType.PLUS
    else
        voucherType = VoucherType.REGULAR
    end

    achievementVouchers["CLASSIC_VICTORY"] = {
        id = "CLASSIC_VICTORY",
        voucherType = voucherType,
        description = "Win Classic mode"
    }

    return achievementVouchers
end

-- Boss trainer voucher generation
local function initBossTrainerVouchers()
    local bossVouchers = {}

    -- Filter trainer configs for boss trainers with vouchers
    -- Conditions: isBoss = true, derivedType != RIVAL, hasVoucher = true
    for trainerType, config in pairs(trainerConfigs) do
        if config.isBoss and config.derivedType ~= TrainerType.RIVAL and config.hasVoucher then
            -- Tier determination based on money multiplier
            local voucherType
            if config.moneyMultiplier < 10 then
                voucherType = VoucherType.PLUS
            else
                voucherType = VoucherType.PREMIUM
            end

            local trainerKey = TrainerType[trainerType]
            local title = config.title and (" (" .. config.title .. ")") or ""
            local description = "Defeat " .. config.name .. title

            bossVouchers[trainerKey] = {
                id = trainerKey,
                voucherType = voucherType,
                description = description
            }
        end
    end

    return bossVouchers
end
```

```lua
-- Step 1: Achievement unlocked (from achievement-engine)

    Action = "AchievementValidated",
    PlayerId = "player_456",
    AchievementId = "CLASSIC_VICTORY",
    Success = "true"
}

-- Step 2: Coordinator checks for voucher award
coordinator-process -> voucher-reward-engine {
    Action = "AwardVoucher",
    PlayerId = "player_456",
    VoucherId = "CLASSIC_VICTORY",
    Source = "Achievement"
}

-- Step 3: Voucher engine awards voucher and updates state
voucher-reward-engine -> coordinator-process {
    Action = "VoucherAwarded",
    VoucherType = "3",  -- GOLDEN
    NewCount = "1",
    Success = "true"
}

-- Step 4: Coordinator updates player progression
coordinator-process -> player-progression-engine {
    Action = "UpdateVouchers",
    PlayerId = "player_456",
    VoucherData = json.encode({
        voucherUnlocks = {...},
        voucherCounts = {...}

-- Step 5: State persistence confirmation
player-progression-engine -> coordinator-process {
    Action = "VouchersUpdated",
    Success = "true"

-- Step 6: Return to client with voucher notification
coordinator-process -> Client {
    Action = "AchievementComplete",
```

### Technical Constraints
[Source: architecture/tech-stack.md]
- **Execution Timeout**: 5-second limit per message handler
- **File Size Limit**: 500KB maximum per process file (target 10-15KB for simple logic)
- **Monolithic Design**: All voucher metadata embedded, no external imports except json
- **Handler Pattern**: Use Handlers.add() with tag matching, not direct assignment
- **Message Protocol**: JSON-encoded data with structured ao.send() responses
- **Timestamp Handling**: CRITICAL - Use msg.Timestamp, NEVER os.time()
- **Error Handling**: Direct validation with ao.send() error responses, avoid unnecessary pcall
- **Tag Values**: All tag values MUST be strings: tostring(number), "true"/"false" for booleans
- **Boss Trainer Data**: Requires embedded trainer configuration subset for voucher generation

### Security Requirements
- **Input Validation**: All player IDs and voucher IDs must be validated before processing
- **Authorization**: Player can only query/modify their own voucher state
- **State Integrity**: Ensure voucher unlock timestamps cannot be forged or manipulated
- **Award Integrity**: Voucher awards must be validated server-side, not client-reported
- **Idempotency**: Multiple award calls for same voucher ID should be safe (already awarded = no-op)
- **Inventory Protection**: Consumption must validate sufficient voucher count before decrementing
