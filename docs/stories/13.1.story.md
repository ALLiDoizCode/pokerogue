### Wild Pokemon Encounter Analysis

#### Core Wild Encounter Components [Source: TypeScript codebase analysis and existing processes]

**1. Species Generation and Area Pools**
- **Area-Based Encounter Tables**: Different biomes/areas have specific Pokemon species pools with weighted probabilities
- **Rarity Tiers**: Common, Uncommon, Rare, Ultra Rare, and Legendary encounter probabilities
- **Level Range Calculation**: Base level + random variation based on area and progression wave
- **Seasonal/Time Variations**: Some species only available under specific conditions

**2. Encounter Rate Calculations**
- **Base Encounter Rate**: Fixed probability per step/action in wild areas
- **Encounter Rate Modifiers**: Items, abilities, and player actions that affect encounter frequency  
- **Area Density**: Different areas have different base encounter densities
- **Avoidance Mechanics**: Player abilities to reduce or increase encounter rates

**3. Wild Pokemon Stat Generation**
- **IV Generation**: Random Individual Values (0-31) for each of 6 stats using deterministic RNG
- **Nature Assignment**: Random nature selection from 25 available natures with stat modifiers
- **Level Calculation**: Base level for area + random variation within defined range
- **Ability Assignment**: Random selection from species' available abilities (including hidden abilities)

**4. Shiny Pokemon Determination**
- **Base Shiny Rate**: Standard 1/4096 probability for shiny Pokemon encounters
- **Shiny Rate Modifiers**: Items, abilities, and progression unlocks that increase shiny odds
- **Shiny Lock**: Certain legendary Pokemon cannot be shiny
- **Shiny Preservation**: Shiny status must be preserved throughout capture process

**5. Special Encounter Conditions**
- **Legendary Encounters**: Special trigger conditions and unique encounter mechanics
- **Event Pokemon**: Time-based or condition-based special encounters  
- **Boss Pokemon**: Enhanced stats, special abilities, guaranteed item drops
- **Roaming Pokemon**: Moving between areas with tracking mechanics

**6. Wild Pokemon AI Patterns**
- **Difficulty Scaling**: Wild Pokemon AI intelligence scales with area difficulty
- **Move Selection Logic**: Probabilistic move selection based on effectiveness and battle state
- **Status Usage**: Strategic use of status moves and healing items
- **Switching Patterns**: Multi-Pokemon wild battles with intelligent switching

**7. Area Restrictions and Availability**
- **Progression Gates**: Certain areas locked behind story/progression milestones
- **Species Availability**: Version exclusives, post-game exclusives, conditional availability
- **Encounter Conditions**: Day/night, weather, season-based availability
- **Constraint Validation**: Ensuring encounters are valid for current game state

### Process Coordination Architecture

#### Cross-Process Communication Pattern
```lua
-- Coordination with existing processes
local function coordinateWildEncounter(encounterData)
    -- 1. Generate Pokemon with pokemon-instance-manager.lua
    local pokemonResult = ao.send({
        Target = POKEMON_INSTANCE_MANAGER_ID,
        Action = "CreatePokemon",
        SpeciesId = encounterData.speciesId,
        Level = tostring(encounterData.level),
        Data = json.encode({
            ivs = encounterData.ivs,
            nature = encounterData.nature,
            ability = encounterData.ability,
            isShiny = encounterData.isShiny,
            isWild = true
        })
    })
    
    -- 2. Initialize battle with battle-engine.lua
    local battleResult = ao.send({
        Target = BATTLE_ENGINE_ID,
        Action = "InitiateBattle",
        BattleType = "WILD",
        Data = json.encode({
            playerId = encounterData.playerId,
            wildPokemon = pokemonResult.pokemon,
            battleSeed = encounterData.rngSeed
        })
    })
    
    -- 3. Update player progression if needed
    if encounterData.isFirstEncounter then
        ao.send({
            Target = PLAYER_PROGRESSION_ENGINE_ID,
            Action = "UpdatePokedex",
            Operation = "seen",
            SpeciesId = tostring(encounterData.speciesId),
            PlayerId = encounterData.playerId
        })
    end
end
```

### Technical Constraints [Source: architecture/tech-stack.md]

**AO Runtime Requirements**:
- **Monolithic Design**: All dependencies embedded in single file, no require() statements
- **Handler Pattern**: Use `Handlers.add()` with tag matching, not direct assignment  
- **Error Handling**: Direct error handling with ao.send() responses, avoid unnecessary pcall usage
- **Performance**: 5-second execution timeout, 500KB file size limit
- **Deterministic Execution**: Use msg.Timestamp, no os.time() or math.random()

**Available AO Globals**:
- `ao.send()` - Message transmission to other processes
- `ao.id` - Process identifier  
- `Handlers` - Message routing system
- `json` - Data serialization for cross-process communication
- Standard Lua: string, table, math (limited subset)

### Security and Validation Requirements [Source: architecture/coding-standards.md]

**Mandatory Behavioral Parity Rules**:
- Never use Lua's math.random() - ALWAYS use AO crypto module for deterministic randomness
- All stat calculations must match TypeScript Math.floor/Math.ceil exactly
- Nature multipliers must be exactly 0.9, 1.0, or 1.1 - never approximate
- All AO message responses must include success boolean
- Never hardcode Pokemon/Move/Item data - always reference database tables
- Battle RNG counter must increment for every random call

**Input Validation**:
- All external data validated and sanitized
- Encounter parameters verified against valid ranges
- Cross-process message validation
- Player state integrity checks
