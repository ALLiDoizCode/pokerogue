## Story Statement
As a **TDD engineer**,
I want **comprehensive aolite-based unit testing framework for AO process handlers and Lua process logic**,
so that **I can write failing tests for Lua handlers first, then implement AO Lua functionality to make tests pass**.

## Acceptance Criteria
1. aolite testing environment configured with concurrent process emulation using coroutines for AO process
2. Message passing test framework validates Lua AO handler responses against expected game action outcomes
3. Handler unit testing covers all game action message types with comprehensive Lua test cases
4. Process state inspection allows validation of ECS world state after Lua handler execution
5. Mock external data sources (Arweave transactions) for isolated Lua handler unit testing
6. Test fixtures provide consistent game state scenarios for reproducible Lua testing
7. Automated test discovery and execution with clear pass/fail reporting for aolite tests
8. TDD workflow documentation guides developers in Lua handler test-first methodology

### API Specifications

#### Test Framework Core API
```lua
-- Test Runner API
aoliteTest = {
    -- Run all tests in a file or directory
    run = function(path) end,
    
    -- Run specific test suite
    runSuite = function(suiteName) end,
    
    -- Register a test suite
    suite = function(name, tests) end,
    
    -- Register a single test
    test = function(name, testFunc) end,
    
    -- Setup/teardown hooks
    beforeEach = function(hookFunc) end,
    afterEach = function(hookFunc) end,
    beforeAll = function(hookFunc) end,
    afterAll = function(hookFunc) end
}
```

#### Assertion API
```lua
-- Assertion Library
assert = {
    -- Basic assertions
    equals = function(actual, expected, message) end,
    notEquals = function(actual, expected, message) end,
    isTrue = function(value, message) end,
    isFalse = function(value, message) end,
    isNil = function(value, message) end,
    notNil = function(value, message) end,
    
    -- Message assertions
    messageEquals = function(actualMsg, expectedMsg) end,
    hasAction = function(msg, action) end,
    hasTag = function(msg, tagName, tagValue) end,
    
    -- State assertions
    stateEquals = function(actualState, expectedState) end,
    stateContains = function(state, expectedSubset) end,
    
    -- Error assertions
    throws = function(func, expectedError) end,
    doesNotThrow = function(func) end
}
```

### Testing Requirements

#### Performance Requirements
- Unit test execution: <100ms per test
- Suite execution: <10 seconds for full suite
- Memory usage: <50MB per test process
- Concurrent tests: Support up to 10 parallel tests

#### Coverage Requirements
- Line coverage: >95% for critical logic
- Branch coverage: >90% for all handlers
- Handler coverage: 100% of defined handlers
- Error path coverage: >80% of error conditions

#### Test Environment Requirements
- Lua 5.3+ compatibility
- No external dependencies (pure Lua)
- Deterministic execution (seeded RNG)
- Isolated test execution (no side effects)
- TAP output format for CI/CD integration

#### Self-Testing Requirements
- Test framework must have >90% self-coverage
- All assertion types must be tested
- Mock system must verify correct behavior
- Process emulation must handle edge cases

### Technical Constraints

#### AO Environment Constraints
- No `require()` statements (monolithic design)
- No file I/O operations
- No network operations
- Limited to AO-provided globals
- 5-second execution timeout
- 500KB process size limit

#### Testing Framework Constraints
- Must work within Lua 5.3 sandbox
- Cannot use external test libraries
- Must be embeddable in single file if needed
- Memory efficient for large test suites
- Compatible with existing test patterns

#### Integration Constraints
- Must integrate with existing CI/CD pipeline
- Compatible with npm test scripts
- Support for test result aggregation
- Exit codes must follow Unix conventions

### Security Requirements

#### Test Isolation
- Each test runs in isolated environment
- No test can affect another test's state
- Mock data cannot leak between tests
- Process IDs must be unique per test run

#### Data Security
- Test fixtures must not contain real user data
- Mock credentials must be clearly marked as test data
- No hardcoded production endpoints
- Sensitive test data must be sanitized in reports

#### Code Injection Prevention
- Test inputs must be validated
- No dynamic code execution from test data
- Message payloads must be sanitized
- Prevent infinite loops in test execution

#### Access Control
- Test framework cannot access production data
- Mock systems must prevent real network calls
- File system access must be restricted to test directories
- Process spawning must be controlled and limited
