### Data Models [Source: architecture/data-models.md#Pokemon Model, Player Model]

#### PC Storage Data Model
```lua
local pcStorageState = {
    -- PC Storage structure
    pcStorage = {
        boxes = {
            -- box[1] through box[30] (expandable)
            [1] = {
                name = "Box 1", -- Default naming, user customizable
                pokemon = {
                    -- pokemon[1] through pokemon[30] per box
                    [1] = "pokemon_instance_id_1",
                    [2] = "pokemon_instance_id_2",
                    -- ... up to 30 Pokemon per box
                    [30] = nil -- Empty slots are nil
                },
                totalStored = 2 -- Count of non-nil Pokemon in this box
            },
            -- ... additional boxes
            [30] = {
                name = "Box 30",
                pokemon = {},
                totalStored = 0
            }
        },
        totalBoxes = 30, -- Default box count, expandable
        totalStored = 0, -- Total Pokemon across all boxes
        currentBox = 1, -- Currently selected box for operations
        maxBoxCapacity = 30, -- Pokemon per box limit
        maxTotalCapacity = 900 -- Total capacity (30 boxes * 30 slots)
    },
    
    -- Party management structure
    party = {
        pokemon = {
            -- party[1] through party[6] - active battle party
            [1] = "pokemon_instance_id_active_1",
            [2] = "pokemon_instance_id_active_2",
            -- ... up to 6 Pokemon in party
            [6] = nil -- Empty party slots are nil
        },
        totalActive = 2, -- Count of non-nil Pokemon in party
        maxPartySize = 6, -- Party size limit
        leadPokemon = 1 -- Index of lead Pokemon (for encounters/battles)
    },
    
    -- Storage metadata
    storageMetadata = {
        totalPokemonOwned = 0, -- Combined party + PC count
        lastModified = 0, -- Timestamp of last storage operation
        storageVersion = "1.0", -- Schema version for migrations
        organizationSettings = {
            autoSort = false, -- Auto-organize Pokemon in PC
            sortCriteria = "level", -- "level", "species", "name", "recent"
            showEmptyBoxes = true -- Display empty boxes in UI
        }
    }
}
```

### Technical Constraints [Source: architecture/tech-stack.md, coding-standards.md]

**AO Runtime Requirements**:
- **Monolithic Design**: All dependencies embedded in single file, no require() statements
- **Handler Pattern**: Use `Handlers.add()` with tag matching, not direct assignment
- **Error Handling**: Direct error handling with ao.send() responses, avoid unnecessary pcall usage for simple operations
- **Performance**: 5-second execution timeout, 500KB file size limit
- **Deterministic Execution**: Use msg.Timestamp, no os.time() or math.random() calls

**Available AO Globals**:
- `ao.send()` - Message transmission to other processes
- `ao.id` - Process identifier
- `Handlers` - Message routing system
- `json` - Data serialization for cross-process communication
- Standard Lua: string, table, math (limited subset)

**Mandatory Behavioral Parity Rules** [Source: architecture/coding-standards.md]:
- Never use Lua's math.random() - ALWAYS use AO crypto module for deterministic randomness when needed
- All storage operations must match TypeScript behavior exactly
- Never hardcode Pokemon data - always reference through Pokemon instance manager
- All AO message responses must include success boolean
- Storage state changes must trigger save data updates
- Party constraints must be identical to TypeScript implementation
